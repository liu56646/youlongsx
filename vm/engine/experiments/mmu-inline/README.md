# TCG ARM MMU regime inlining — opt-in candidate

The existing `regime_el()` body is preserved verbatim and marked
`always_inline`. This lets the compiler see repeated local regime decoding
inside TCG's ARM page-table and permission helpers. It adds no cache or epoch,
skips no invalidation and removes no permission/exception check. CPU and
snapshot layouts remain unchanged; existing engine-identity guards still
apply to old RAM snapshots.

The full QEMU build now supports `VMHOST_TCG_REGIME_INLINE=1`; **default is 0**.
The patch also removes its annotation when disabled in a reused source tree.
It is not installed into the current app or enabled in a production APK.

The independent Windows builder layers this change onto the 0.2.11 native
RCU engine. It does not combine the separate PTW-context, core-TLS, TTBR-ASID
or populated-bank experiments. Source objects and previous binaries remain
untouched and their hashes are checked.

```powershell
python vm/engine/experiments/mmu-inline/build_candidate.py --engine-root D:\youlong-fast-build\engine-native --rcu-candidates D:\youlong-fast-build\checks\rcu-native-tls-candidates --ndk "$env:LOCALAPPDATA\Android\Sdk\ndk\28.2.13676358" --out D:\youlong-fast-build\checks\mmu-inline-new
python vm/engine/experiments/mmu-inline/run_device_checks.py --adb D:\platform-tools\adb.exe --serial YOUR_DEVICE_SERIAL --build D:\youlong-fast-build\checks\mmu-inline-new --out D:\youlong-fast-build\checks\mmu-inline-device-new
```

Use new output directories. The device runner refuses an already running VM,
requires a cool phone, checks uploaded hashes, uses only unique temporary
files, and cleans them up. It pins the small workload to CPU 6 without forcing
frequency. It does not launch an installed app, attach disks, alter properties
or read/write an Android instance.

## Recorded results, 2026-10-26

The real production LPAE function and its permission helpers were compiled
twice with identical physical-bus/QOM/logging boundary models. Across 32768
deterministic cases, both variants produced 3117 successes, 29651 faults and
the same complete-result/descriptor-trace digest `dedd99a82886885c`. Cases
vary AArch32/AArch64, EL1/2/3, secure/nonsecure regimes, endianness, page
granules, TTBR ranges/TBI, permission/AF faults and external read errors.
Nested S1-to-S2 page walks and real concurrent page-table modification are
not independently validated by this model.

`mmu_guest.c` is a separate real TCG workload: one virtual CPU, 64 MiB, an
ARM64 virt board, actual four-level stage-1 tables, 8000 explicit TLB
invalidations and 32 pages read/written and checked after each invalidation.
All memory mappings and bus operations in this test use actual QEMU code.
It prints its virtual-counter interval and checksum, then normally powers
off the emulated board through PSCI. It never reboots the host phone.

Both independent batches use ABBA repeated three times, six samples per
variant. Counter intervals exclude engine/renderer startup:

| Batch | Original median | Inline median | Interval reduction in this workload |
| --- | --- | --- | --- |
| Initial | 53.287728 ms | 51.757872 ms | 2.87% |
| Full recipe reproduction | 53.194008 ms | 51.642288 ms | 2.92% |

Every guest checksum was `4397496755294080000`, every process exited with
code 0, and temporary files were removed. This is **not** Android cold boot,
app launch, multi-vCPU contention, App-domain behavior or finger-to-display
latency. No complete-system speedup is claimed.

Inlining also grows the disassembled instruction sample: the combined
selected-function sample changes from 935 to 992 instructions, while its
out-of-line `regime_el` calls change from 11 to 0. Code growth may affect
other workloads, which is why this remains an opt-in candidate.

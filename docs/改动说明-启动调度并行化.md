# 启动调度修正（2026-10-18）

## 原因

手机 `cc96ded5` 上的实际启动参数是 `tcg,thread=multi -smp 6`，
但 `libsigfix.so` 在构造函数中把整个 QEMU 进程限制到 CPU 6、7。
所有新线程继承这个限制，六个 vCPU、图形和 I/O 线程只能争用两个核心。
旧注释把启动早期只有一个忙线程误认为引擎是单线程 TCG。

## 修改

- 引擎启用 QEMU 的 `-name vmhost,debug-threads=on`。
- `libsigfix` 在 `pthread_setname_np` 成功后识别 `CPU 0/TCG`，只把启动
  vCPU 限制到当前允许集合中最高频的核心。单线程模式的 `ALL CPUs/TCG`
  同样保留大核优先。
- 其余线程保留原始允许集合，由宿主调度；不改 CPU 频率、温控或系统 cpuset。
- 不能读取亲和性或最高频率时不干预。显式 `VMHOST_PIN_CPUS` 仍按原语义处理。
- 引擎默认设置 `VMHOST_GFX_DEBUG=0`，关闭 gfxstream 的 fine 日志；错误日志保留。

## 验证

- `:app:assembleRelease` 成功，包含 release lint 检查。
- 真机运行 `test_sigfix_affinity.c`：默认、legacy、禁用绑核、显式 `c0`
  掩码，以及 `taskset 0f` 限制允许集合，五组测试均通过。
- 覆盖安装 release APK 成功，保留原有实例数据。
- 新版实际 QEMU 进程：`CPU 0/TCG` 为 `6-7`，`CPU 1/TCG` 至
  `CPU 5/TCG`、I/O 线程及进程主线程为 `0-7`。
- 实际子进程环境确认 `VMHOST_GFX_DEBUG=0`、`VMHOST_PIN_MODE=balanced`。

以上验证证明原来的两核限制已解除，不等于完整开机时间的收益测量。
Android 初始化仍由 TCG 执行，串行阶段、镜像首次 dexopt、温控都会影响耗时；
不能据此承诺秒开或固定百分比提速。

## 复测与回退

在同一镜像、同一数据盘状态、接近的温度下对比；每次设置后正常停止并重新启动实例。

```sh
# 临时恢复旧的全进程绑核策略
adb shell setprop debug.vmhost.pin_mode legacy
# 恢复新版默认策略
adb shell setprop debug.vmhost.pin_mode balanced
# 仅排障时打开图形详细日志；0 恢复关闭
adb shell setprop debug.vmhost.gfx_debug 1
```

原生库由 `vm/build-aosp-exp/build_sigfix.sh` 重建；它的产物
`vm/engine/src/main/jniLibs/arm64-v8a/libsigfix.so` 随 APK 分发。
修改 C 源码后须先重建该库，再执行 Gradle 打包。

本次 APK、旧版备份及采样日志保存在本地 `dist/boot-optimization/`（不入 Git）。

## 开机时间实测（2026-10-18 补测，headless 手工 harness）

前一轮只验证了绑核策略生效，没有完成整机启动时间对比。补测用一份同时适用于
两种模式的 headless QEMU harness（[vm/build-aosp-exp/ab_boot_headless.sh](../vm/build-aosp-exp/ab_boot_headless.sh)）跑完整冷启动：参数与引擎 p11 路径一致
（`-M ranchu -cpu cortex-a57 -smp 6 -m 3072 -accel tcg,thread=multi -tb-size 512`，
virtio-gpu-pci、virtio-tablet/keyboard、`-display none`、串口写文件），
**额外补上引擎在父进程里设置的关键环境变量 `VMHOST_DT_FSTAB=none`**
（p11 的 system.img 是独立 ext4；不设置时 QEMU 会按 legacy 下发 DT fstab，
访客 init 找不到 system/vendor 分区，启动到 16s 就 `InitFatalReboot`）。

- 两次运行前都恢复同一份 4GB `userdata.img` 基线（已完成首次 dexopt），
  排除首次 dexopt 差异；只改 `VMHOST_PIN_MODE`。
- 指标：访客内核时间戳到 `sys.boot_completed=1` 的时刻（QEMU 虚拟时钟与
  宿主单调时钟基本一致，与 wall 实测相差 <3%）。
- 温度/频率：开机功率大且未主动冷却，两组热状态并不完全一致，见下表。

| 项 | legacy（全进程钉 6/7） | balanced（仅 CPU 0/TCG 钉 6/7） |
|---|---|---|
| `sys.boot_completed=1`（guest 内核时间） | **665.0 s** | **676.8 s** |
| 墙钟（含 QEMU 启动） | 674 s | 694 s |
| ZygoteInit 完成 | 148.6 s | 169.2 s |
| system_server 就绪 | 192.1 s | 228.0 s |
| PMS 首次扫描完成 | 337.1 s | 385.3 s |
| UpdatePackagesIfNeeded | 17.6 s | 20.2 s |
| 开局电池 / cpu6 频率上限 | 35.5 °C / 2.246 GHz | 36.2 °C / 2.438 GHz |
| 结束时 cpu6 频率上限 | 1.958 GHz | 1.958 GHz |

结论：单次对比 balanced 比 legacy **慢 1.8%**，差异在宿主调度/温控抖动范围内；
早段（zygote→system_server）偏慢、后半段（SystemServer 各 boot phase）反而略快。
**这组数据既不能证明 balanced 带来冷启动提速，也谈不上明显劣化。**
保留 balanced 作为默认（它修正了 MTTCG 下把 vCPU/渲染/IO 全部钉两核的概念错误，
且提供 `debug.vmhost.pin_mode legacy` 回退）；若要定论，需要在相同温度、
相同 cpufreq 上限下做多轮交替测量（建议每模式 ≥3 轮取中位数）。

顺带结论：同一份已 dexopt 的数据盘，headless 冷启动约 665–677 s；而首次
启动（dexopt 未完成）那次是 983 s，其中 `UpdatePackagesIfNeeded` 一项就
179 s——首次启动比后续多 3–5 分钟，属一次性开销，不是每次启动都付。

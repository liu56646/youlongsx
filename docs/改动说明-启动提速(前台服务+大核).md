# 改动说明：实例常驻前台服务 —— 启动期拿满大核、不被冻结

> 目的：解决「开启要 150 秒」里**与访客自身无关**的那部分损失 —— 实例进程在启动
> 期间被 Android 降级到 background cpuset / 进入 doze，拿不到大核，甚至整段停住。
> 影响面：宿主侧进程等级与调度，不改引擎参数、不改访客镜像。

---

## 1. 问题（真机实测）

测试环境：真机 `cc96ded5`（骁龙 8 Elite 平台，11GB RAM）/ 访客 `p11_arm64` /
3072MB / 6 vCPU / 720x1280，`QEMU_TCG`（真机打不开 `/dev/kvm`）。

1. **进程等级掉档。** 实例 Activity 不是当前焦点窗口时（锁屏、切走、通知栏遮挡），
   Android 把 `:vm1` 进程放进 `background` cpuset：

   ```
   /proc/<qemu>/cpuset        -> /background
   Cpus_allowed_list          -> 0-3          # 3.53GHz 那组
   ```

   而 `foreground` / `top-app` cpuset 是 `0-7`，包含 6、7 两个 4.32GHz 大核。
   `libsigfix.so` 的 VMHOST_PIN 只能在「允许集合里」挑最高的，于是只能钉到 `0,1,2,3`。

2. **doze 下掉速更狠。** 屏幕灭掉后 guest 内核时间的推进从 ~1:1 掉到约 **1:6**
   （100 秒墙钟只跑出 17 秒 guest 时间），甚至出现整段 QEMU 全部线程 sleeping、
   0% CPU 的停住。

3. **QEMU 是 fork 出来的子进程**，与父进程同 cgroup：父进程被冻结/降级，它跟着吃
   同样的待遇，所以这件事没法只在引擎侧解决。

## 2. 改法

- 新增**实例前台服务**（`VmInstanceService1..4`，各自与同名实例 Activity 同进程），
  由 `VmNativeActivityBase.onCreate` 拉起、`onDestroy` 停止：

  ```
  startForegroundService(VmInstanceServiceN)
      -> startForeground(id, 常驻通知, FOREGROUND_SERVICE_TYPE_SPECIAL_USE)
      -> acquire(PARTIAL_WAKE_LOCK)
  ```

  targetSdk 35 起 `specialUse` 必须声明类型与子类型，见
  `AndroidManifest.xml` 的 `FOREGROUND_SERVICE_SPECIAL_USE` 与
  `PROPERTY_SPECIAL_USE_FGS_SUBTYPE`。

- 服务与 Activity 都在 `:vmN` 进程里，QEMU 子进程随之整段生命周期保持前台服务等级。
- 全部包在 `runCatching` 里：拿不到前台服务等级时退回原来的行为，不会把实例起不来。

## 3. 效果（真机实测，同一镜像 / 同一实例数据）

| 指标 | 改前（/background，0-3） | 改后（/foreground，6-7） |
|---|---|---|
| QEMU 的 cpuset | `/background`，`Cpus_allowed_list: 0-3` | `/foreground`，`Cpus_allowed_list: 6-7` |
| VMHOST_PIN 落点 | `0,1,2,3`（集合内最高频） | `6,7`（4.32GHz 大核） |
| zygote 就绪 | 153.3s | 130.7s |
| system_server 进入 | 197.5s | 184.4s |
| PackageManagerService 启动 | 215.4s | 202.3s |

即：不改变访客本身的工作量，启动期就能稳定落在最高主频的大核上；
更重要的是**锁屏/切后台时不再掉到低档、也不会停住**。

## 4. 顺带落地的 A/B 开关

`-cpu` 型号（TCG 分支）支持真机覆盖，便于不改 APK 做对照实验：

```bash
adb shell setprop debug.vmhost.cpu max    # 打开本版 QEMU 支持的全部特性（含 LSE/crc/crypto）
adb shell setprop debug.vmhost.cpu ''     # 回到默认 cortex-a57
```

默认值仍是 `cortex-a57`，不改变现有行为；`max` 的收益尚未拿到可信 A/B 数据
（见第 5 节）。

## 5. 还没做 / 下一步

1. **`-cpu max` 的 A/B 尚未定论。** 需要一台温度可控、屏幕常亮的机器跑对照，
   本机在连续重负载后出现明显热降频（policy0 从 3.53GHz 掉到 2.4GHz、policy6 掉到
   1.0GHz），会污染结论。
2. **冷启动本体**（kernel→init→zygote→system_server→PMS 扫描）在 TCG 下是单 vCPU
   线程瓶颈（实测只有 1 条线程 100%，宿主 8 核里 6.8 核空闲），要再快只能靠换 QEMU
   基座（见 `vm/engine/scripts/QEMU基座升级-移植指南.md`）。
3. **quickboot（「别冷启动」）** —— 见第 6 节，已做可行性实测，结论是**当前这套
   ranchu/gfxstream 的迁移流还不能原样回灌**，需要 QEMU 侧配合。

## 6. quickboot 可行性实测（2026-10-16，真机）

结论先行：**传输侧没有任何问题，卡在 QEMU 的加载侧。**

做法：用引擎现成的 QMP 调试端口 + 设备本地落盘，把整机迁移流抓成一份
`snapshot.bin`（`vm/tools/qmp_snapshot.py` 就是这个用途的工具），再放到实例目录里
让引擎按既有的 `-incoming unix:…` 路径喂回去。

| 环节 | 结果 |
|---|---|
| QMP `migrate tcp:127.0.0.1:<port>` 导出整机状态 | ✅ 成功 |
| 吞吐 | **270 MB/s**（设备本地回环；同一份操作走 `adb reverse` 只有 16 Mbps，所以快照必须落在设备本地，不能走 adb） |
| 体积 | 抓取那一次 696MB（guest 内存 3072MB，只传了实际使用的页） |
| 用 `-incoming` 喂回 QEMU | ❌ `Unknown ramblock "", cannot accept migration` → `load of migration failed: Invalid argument` → exit(1) |

失败点在 RAM 段。日志里能看到 aemu 的快照钩子在加载路径上确实被调用
（`VMHOST_MIG_ZERO_LOAD 0000:00:0b.0/goldfish_address_space_area …`、
`VMHOST_MIG_ZERO_LOAD virtio-gpu-host-coherent …`），说明这套 QEMU 的迁移/快照
路径被 Android 模拟器改过：它期望的是模拟器自己的 snapshot 框架（仓库里已经链了
`libgfxstream-snapshot.a`），而不是一条裸的 socket 迁移流。

**换句话说：quickboot 不是"补上保存侧"就完事，还要对着 QEMU 侧把加载路径打通**
（走 aemu 的 snapshot API，把宿主渲染器状态一起存/取）。这是独立的一摊工作量，
在动手之前值得先确认收益是否能兑现。

## 7. 顺带修掉的两个真 bug（都为 quickboot 铺路）

为了不给用户留下"一个坏快照 = 永远黑屏"的坑，补了**坏快照自动回退**：恢复启动的
QEMU 只要早早退出，就删掉 `snapshot.bin` 并按冷启动重来一次。做这件事时发现两处
早就存在、但一直没被触发的缺陷：

1. **`vm_qemu_is_running()` 在子进程模式下永远返回 true。** 它回落到 `s_running`，
   而那个标志只在 `stop()/reset()` 里清 —— 子进程崩溃时它还是 true，于是
   「QEMU 已停止运行」这条分支从来没走过，僵尸进程也收不掉。
   现在子进程模式直接以 `child_alive()` 为准。
2. **没有窗口时 `ALooper_pollOnce(-1)` 会永久阻塞。** 每秒一次的 QEMU 存活检查
   挂在这个循环上，无窗口时它根本不执行（实测：实例退到后台时 QEMU 崩了没人管）。
   改成无窗口时也用 1s 超时，并把检查从"每 60 轮"改成按时间判断。

真机验证（故意塞一个 4KB 垃圾 `snapshot.bin`）：

```
检测到快照，QEMU 以 -incoming … 恢复
QEMU 已停止运行（退出原因见上一条 VmQemu 日志）
快照恢复失败：QEMU 没接受迁移流，删除快照后回退冷启动
已拉起子进程 QEMU（ranchu 模式）…     ← 冷启动重来
```

`snapshot.bin` 被删除，访客正常冷启动到 `boot_completed`。

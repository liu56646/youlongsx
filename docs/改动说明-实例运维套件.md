# 改动说明：实例运维套件（事件日志 / 快照存档 / 存储清理 / 诊断包）

> 目的：补上宿主侧的「可运维性」。此前排障信息散落四处（引擎串口日志、配置快照、探测报告），
> 且没有「回到某个更早的存档点」与「存储去哪了」的能力；用户报告问题时，来回索要证据效率极低。
> 影响面：纯宿主侧（`core-vm` 新增 4 个类 + `app` 轻量接线），**不改引擎、不改镜像格式、不动业务盘**。

---

## 1. 新增能力一览

| 能力 | 入口类 | 用户视角 |
|---|---|---|
| 实例事件日志 | `VmLogStore` | 「宿主对这个实例做过什么」有了带时间轴的本地证据 |
| 快照存档 | `VmSnapshotStore` | 把引擎的滚动快照复制成命名存档，可回滚 |
| 存储盘点 / 清理 | `VmStorageStats` | 一屏看清镜像/实例/垃圾各占多少，一键安全清理 |
| 诊断包 | `VmDiagnostics` | 一个 zip 打包全部排障证据，直接分享 |

## 2. 设计动机与取舍

### 2.1 VmLogStore：宿主侧事件日志

引擎已有 `<dataDir>/logs/console.log`（QEMU 串口 + stderr），回答的是「**guest 里**
发生了什么」；但「宿主给了什么配置、用户做了什么操作」没有落点。排障时两边对不上 ——
比如「这次启动到底给了多大内存」，得去翻已经覆盖的 config.json。

- 落点：`vm_<id>/logs/events.log`，与 console.log 同住一个目录，天然按实例聚合；
- 格式：`2026-10-31 12:00:00.123 I/Launcher 启动 虚拟机 1：backend=QEMU_TCG mem=3072MB cores=6`；
- 轮转：单段 256KB、保留 3 段（写前检查 + 同目录 renameTo，断电最多丢当前段尾部）；
- 清理：按天 prune 只删轮转段，活跃段永不删。

**取舍**：写失败静默返回 false —— 日志永远不能反过来阻断业务（启动 / 删除实例
不能因为磁盘满而失败）。

### 2.2 VmSnapshotStore：快照存档（命名副本）

引擎的快照链路（aemu quickboot，保存 1.3s / 恢复 3.7s）只有**一份无名、滚动覆盖**
的「最近状态」。本类用「复制存档」实现命名存档点，**不改引擎**：

- `save`：live 快照（`snapshot.bin`）复制为 `snapshots/<id>/snapshot.bin` + 元数据登记；
- `restore`：复制回 live 位，原 live 先备份为 `snapshot.bin.bak`（可反悔）；
- `reconcile`：外部因素删掉载荷后的孤儿对账；`prune`：按份数瘦身。

**能力边界（有意声明）**：快照只含执行状态（RAM / 设备状态），不含数据盘。
存档后访客写入 userdata 的内容不会被恢复回滚 —— 与「游戏存档 ≠ 磁盘时光机」同理。
磁盘级回滚需要复制 4GB 数据盘，成本完全不同，不在这个 PR 里假装支持。

**安全**：save / restore 在实例运行中被拒绝（复制正在被改写的执行状态必然自相
矛盾）；任何操作都不碰 userdata / metadata / product 业务盘。

### 2.3 VmStorageStats：盘点与清理

镜像 ~500MB、实例 4GB 起步、快照几百 MB 一份，「存储去哪了」是这类应用的第一差评源。

- `scan`：把 `files/images`、`files/vms`、`cacheDir` 三棵树盘点成**带业务语义**的
  条目（IMAGE / INSTANCE_DATA / INSTANCE_SNAPSHOT / 下载残段 / 导入暂存 / 孤儿目录…）；
- `clean`：默认只删残段 + 暂存；孤儿目录（index 丢失的实例目录）**仅在列出供排查**，
  要删必须显式传 `includeOrphans=true`（本 PR 的 UI 不传，后续可加二次确认交互）；
- 实例日志不进一键清理：它是排障证据，专用路径是 `VmLogStore.pruneOlderThanDays`。

**实现细节**：`clean` 按 `scan` 产出的条目回查路径删除，**永远不碰**
IMAGE / INSTANCE_* 分类 —— 调用方传错参数也不会误删业务数据。

### 2.4 VmDiagnostics：诊断包

`VmDiagnostics.builder()` 按顺序收节（设备预检 / 探测报告 / 存储盘点 / 实例配置 /
事件日志尾部 / 引擎串口尾部），打成单个 zip：

- 节名带两位序号前缀，解包后的排序即排障阅读顺序（环境 → 配置 → 日志）；
- `manifest.json` 记录生成时间与各节状态；**缺节不失败** ——「console.log 不存在」
  本身就是线索；
- 大日志只收尾部 256KB（`addFileTail`，截断点落在行中间时丢掉残行）；
- 先写 `.tmp` 再原子 rename，分享目录不会被扫到半成品 zip。

## 4. 测试与验证

- 全部新逻辑为纯 JVM（只依赖 `java.io.File` / `org.json`），`./gradlew :core-vm:test` 覆盖：
  - 日志：格式、多行缩进、轮转链位移与保留份数、写满自动轮转、tail 跨段拼接、
    按天清理、4 线程并发不丢行；
  - 快照：无 live / 运行中被拒、保存复制载荷、重名自动后缀、恢复备份原 live、
    孤儿对账、index 损坏按空处理、prune 留新、统计只算在档载荷；
  - 存储：十类条目分类、字节账本、dry-run 不落刀、默认清理不动业务数据、
    `includeOrphans` 才删孤儿、日志不进清理；
  - 诊断包：节序与 manifest、缺节不失败、尾部截取丢残行、节名清洗；
  - `VmConfigTest`：JSON 往返 / 缺省回退 / 未知枚举降级 / 默认档位钉死（3072MB / 6 核）。
- UI 侧（真机）：长按实例 →「导出诊断包」得到 zip；「存储清理」弹盘点报告，
  确认后 toast 释放量；`events.log` 随创建/启动/停止/删除自动累积。

## 5. 后续（不在这个 PR）

- 事件日志接入更多节点（下载进度节点、provisioning 结果）；

### 1.1 怎么做到「装到手机上点一次就跑」

镜像不能进 APK（单个 3 GB），所以走**首启下载**：

1. **托管镜像包**：把 `vm/dist/*.zip` 传到任意能给出 **https 直链**的地方
   （对象存储、图床、网盘直链都行），**放在同一个目录下**。
   App 会按 `<基址>/<tag>.zip` 取，所以加版本只是多放一个文件，不用改 App。

   | 文件 | 访客系统 | 大小 |
   |---|---|---|
   | `p71_arm64.zip` | Android 7.1 (API 25) | 291 MB |
   | `p9_arm64.zip` | Android 9 (API 28) | 392 MB |
   | `p11_arm64.zip` | Android 11 (API 30) | 506 MB |
   | `p13_arm64.zip` | Android 13 (API 33) | 622 MB |

2. **构建时注入基址**：

   ```powershell
   cd k:\youlongsx\vm
   .\gradlew.bat -PguestImageBaseUrl="https://你的域名/vm" :app:assembleDebug
   ```

   只用一个版本时也可以用 `-PguestImageUrl="https://…/p11_arm64.zip"`。
   两个都不注入也能构建，只是启动时会提示改用「导入镜像」选本地 zip。

3. **装到手机、点「一键启动」**：App 会依次
   下载镜像（带进度条、支持断点续传）→ 解压到应用私有目录 → 自动建一个实例 → 启动虚拟机。

**没有服务器时的兜底**：点「导入镜像」，从文件管理器选 zip 即可
（走 SAF，流式解压，不需要先拷成临时文件）。

**选版本**：点「新建实例」会弹出访客系统版本列表，每项都标了
`已就绪 / 未下载`，选哪个版本就为哪个版本下载镜像。不同实例可以用不同版本。

> 下载体积说明：`system.img` 是 3 GB 左右的 ext4，但里面大量空块，zip 压缩后只有
> 300~620 MB。这是每个版本首启需要下载的量，一次即可，之后一直复用。

## 2. 访客系统镜像

### 2.1 获取（跳过 AOSP 编译）

用 **AOSP default**（无 Google 服务）而不是 google_apis：两者 `system.img` 一样是 3.0 GB，
但 default 少了 GApps，访客侧启动的服务更少，TCG 软件模拟下开机更快。

```powershell
$env:ANDROID_HOME = "C:\Users\liu\AppData\Local\Android\Sdk"
& "$env:ANDROID_HOME\cmdline-tools\latest\bin\android.exe" `
    sdk install "system-images;android-30;default;arm64-v8a"
```

> 用旧版 `sdkmanager.bat` 会把 `system-images;android-30;...` 按 `;` 拆坏，
> 报 "Package system-images not found"。用 `android.exe sdk install` 正常。

实测目录内容：

```
system.img                    3,083.0 MB
vendor.img                       49.0 MB
encryptionkey.img                18.0 MB
kernel-ranchu                    12.9 MB
ramdisk.img                       1.6 MB
userdata.img                      1.0 MB    ← 已格式化的空 /data，必须带上
```

**打成可下载的 zip**（根目录直放，不套一层目录；`VmImageProvider` 依赖这个结构）：

```bash
SRC=/mnt/c/Users/liu/AppData/Local/Android/Sdk/system-images/android-30/default/arm64-v8a
mkdir -p /tmp/vmk /mnt/k/youlongsx/vm/dist && cp "$SRC/kernel-ranchu" /tmp/vmk/kernel
zip -6 -j /mnt/k/youlongsx/vm/dist/p11_arm64.zip /tmp/vmk/kernel \
    "$SRC/system.img" "$SRC/vendor.img" "$SRC/ramdisk.img" "$SRC/userdata.img"
```

产出的 `p11_arm64.zip` **506 MB**（3.3 GB 未压缩，`system.img` deflate 85%）。
用 `-j` 是为了把 `kernel-ranchu` 以 `kernel` 的名字放进 zip，避免先把 3 GB 拷到临时目录。

> **`userdata.img` 不能省**：Android 的 `/data` 必须是已格式化的 ext4/f2fs。
> 直接给一个全零文件，访客首启会卡在挂载 `/data`。
> `VmDiskStore.ensureUserData()` 会把它拷成实例的数据盘再稀疏扩容。

> **授权提醒**：Google 的 emulator 镜像面向模拟器，随 App 分发有授权风险。
> 个人研究可以；要分发请走 §2.3 自编 AOSP。

### 2.2 多版本镜像（直接拉取，不占 C 盘）

`sdkmanager` 会把镜像装进 SDK 目录（C 盘），每个版本约 3 GB —— 本机 C 盘放不下。
所以提供 [make_guest_image.sh](../vm/tools/make_guest_image.sh)：**直接从 Google 仓库拉压缩包，全程用 K 盘**。

```bash
cd /mnt/k/youlongsx/vm/tools
./make_guest_image.sh 28          # Android 9  → dist/p9_arm64.zip
./make_guest_image.sh 33 default  # Android 13 → dist/p13_arm64.zip
```

脚本做的事：

1. 拉 `sys-img/android/sys-img2-1.xml`，用 [list_sysimg.py](../vm/tools/list_sysimg.py)
   解析出该 API 版本 arm64 镜像的**真实直链**（不走 sdkmanager，SDK 目录零占用）；
2. 下载到 `/tmp`，解压；
3. 按 `kernel / system.img / vendor.img / ramdisk.img / userdata.img` 的**扁平结构**打成 zip
   （`kernel-ranchu` 会被改名成 `kernel`）；
4. 产出 `dist/<tag>.zip` 并清理临时目录（`--keep` 可保留排查）。

**已验证可用的版本**（布局都是经典的 `system.img + vendor.img`，与本引擎兼容）：

| API | tag | zip 大小 | 备注 |
|---|---|---|---|
| 25 | `p71_arm64` | 291 MB | 无 `vendor.img`，引擎会自动跳过 |
| 28 | `p9_arm64` | 392 MB | |
| 30 | `p11_arm64` | 506 MB | |
| 33 | `p13_arm64` | 622 MB | |

**未知数**：Android 13 及以上（API 34+）的部分镜像改用 `super.img` 动态分区，
脚本在这种情况下会找不到 `system.img` 并直接报错退出（本引擎只支持经典布局）。
真机能不能带起 7.1 / 13 也还没验证过 —— 内核与 `-M virt` 的配合需要实测。

新增版本后，把条目补进
[VmGuestCatalog](../vm/core-vm/src/main/kotlin/com/vm/core/VmGuestCatalog.kt) 的 `ALL` 列表，
App 的版本选择框就会自动出现。

## 3. QEMU 交叉编译（已跑通）

### 3.1 一键执行

```bash
wsl -d Ubuntu
cd /mnt/k/youlongsx/vm/engine/scripts
sed -i 's/\r$//' wsl_bootstrap.sh build_qemu.sh   # 脚本来自 Windows，需转 LF
chmod +x *.sh
JOBS=8 ./wsl_bootstrap.sh    # 阶段一：NDK + 依赖链（约 10 分钟）
WORKDIR=/root/vmbuild JOBS=8 ./build_qemu.sh     # 阶段二：QEMU 本体（约 20 分钟）
```

### 3.2 依赖链

QEMU 强依赖 `glib-2.0` 与 `pixman-1`，NDK 都不带：

```
zlib(PIC) → libffi → pcre2 → glib-2.0
pixman-1（独立）
libslirp  ← 只为 `-netdev user`（用户态 NAT）
```

关键参数（`wsl_bootstrap.sh` 已固化）：

- **libslirp 必须自己编**：QEMU 的 meson 写的是 `dependency('slirp', method: 'pkg-config')`，
  **没有配 fallback**，所以它不会自动去用 `subprojects/slirp.wrap`。
  脚本按 wrap 里 pin 的 revision（`26be815b`）克隆并交叉编译，装进 sysroot 让
  `pkg-config --exists slirp` 成立，QEMU 才能启用 `-netdev user`。

- **API = 28**：bionic 的 `iconv` 从 API 28 起提供，glib 依赖它。App `minSdk` 同步为 28。
- **zlib 必须显式 `-fPIC`**：zlib 的 Makefile 不会自动加，aarch64 上会报
  `relocation R_AARCH64_ADR_PREL_PG_HI21 cannot be used against symbol 'z_err_msg'; recompile with -fPIC`。
- **glib 的 meson 选项**：`-Ddtrace` / `-Dsystemtap` 是**布尔**选项，不能传 `disabled`；
  `-Dman` 在 meson 1.3 里已改名 `man-pages`。最终用 `-Dtests=false -Dnls=disabled -Dselinux=disabled -Dlibmount=disabled`。
- **glib 强制要求 gettext**（源码注释写明 "We require gettext to always be present"），
  关掉 NLS 也会去要 `intl`，因此**不能加 `--wrap-mode=nodownload`**，要放开让它拉 proxy-libintl。
- **不要设 `PKG_CONFIG_SYSROOT_DIR`**：`.pc` 里的 prefix 已是真实绝对路径，再设会双重拼接。

### 3.3 QEMU 本体的坑（都已在 `build_qemu.sh` 里处理）

| 现象 | 原因 | 处理 |
|---|---|---|
| `Pkg-config for machine host machine not found` | QEMU 会找带 cross-prefix 的 `llvm-pkg-config` | 生成包装脚本，强制只在 sysroot 内查找 |
| `sizeof(size_t) doesn't match GLIB_SIZEOF_SIZE_T` / `'time.h' file not found` | `--extra-cflags` 里的 `--sysroot` 覆盖了 NDK 自带 sysroot | 去掉 `--sysroot`，只留 `-I/-L` |
| `redefinition of 'vring'`（libvhost-user） | QEMU 自带 `standard-headers` 与 bionic 内核头冲突 | `--disable-vhost-user --disable-vhost-user-blk-server` |
| `expected ';' at end of declaration list`（9p-marshal.h） | bionic 把 `st_atime_nsec` 等定义成了宏 | 打补丁插入 `#undef`（幂等） |
| `call to undeclared function 'shm_open'` | bionic 未实现 POSIX 共享内存（`_POSIX_SHARED_MEMORY_OBJECTS` 缺失） | 对 3 个使用点插入返回 `ENOSYS` 的本地实现 |
| 链接 `libvmengine.so` 报 `R_AARCH64_ADR_PREL_PG_HI21 cannot be used against symbol 'cpuinfo'; recompile with -fPIC` | QEMU 默认用 **`-fPIE`** 编译，PIE 对全局符号的取址方式不允许出现在共享库里 | `--disable-pie` + `--extra-cflags=-fPIC` 重编（**嵌入 .so 的必要条件**） |

补丁全部由 `build_qemu.sh` 幂等施加，重新 clone 源码后重跑即可复现。

### 3.4 打包静态产物（B 方案用）

QEMU 的 meson **不产出** `libcommon.a` / `libqemu-aarch64-softmmu.a`，
而是把对象文件直接喂给最终可执行体。因此需要按 `build.ninja` 里
`qemu-system-aarch64` 的真实链接输入还原静态库：

```bash
WORKDIR=/root/vmbuild ./package_qemu_static.sh
```

该脚本做三件事：

1. 从 `build.ninja` 的 build 行取出全部对象文件 → 打成 `libqemu_objs.a`（约 160 MB）；
2. 从 `LINK_ARGS` 取出 `libqemuutil.a` / `libfdt.a` / `libvduse.a` / `libz.a`；
3. **把瘦归档（thin archive）重打包成普通归档**——meson 产出的 `.a` 以 `!<thin>` 开头，
   成员只是相对路径，直接拷贝会报
   `could not get the buffer for a child of the archive: ... No such file or directory`。

产物落在 `engine/src/main/cpp/prebuilt/qemu/arm64-v8a/`。

### 3.5 产物布局

```
engine/src/main/jniLibs/arm64-v8a/          ← 随 APK 分发
  libglib-2.0.so / libgio-2.0.so / libgobject-2.0.so / libgmodule-2.0.so
  libpixman-1.so / libpcre2-8.so / libffi.so / libintl.so

engine/src/main/cpp/prebuilt/qemu/arm64-v8a/ ← 不进 APK
  libqemu_objs.a        160 MB   1158 个对象的普通归档
  libqemuutil.a          17 MB
  libfdt.a / libvduse.a / libz.a
  libqemu-system-aarch64.so  31 MB   独立可执行体（参考/回退用，已不进 APK）
```

依赖闭包由 `build_qemu.sh` 用 `readelf -d` 递归收集，自动跳过系统库。

> `libqemu-system-aarch64.so` 只是留档：QEMU 已静态链入 `libvmengine.so`，
> 不再需要它以子进程方式运行，所以不随 APK 分发（可省约 6 MB）。

## 4. 显示链路：当前实现（B 方案）

已按 **B 方案**落地：把 QEMU 静态库链进 `libvmengine.so`，自己写入口驱动。

### 4.1 嵌入点

QEMU 的 `system/main.c` 只有三行：

```c
int main(int argc, char **argv)
{
    qemu_init(argc, argv);
    return qemu_main();
}
```

真正的入口都在静态库里。我们只声明这三个符号、不引入任何 QEMU 头文件
（见 [vm_qemu.c](../vm/engine/src/main/cpp/src/vm_qemu.c)）：

```c
extern void qemu_init(int argc, char **argv);
extern int  qemu_main_loop(void);
extern void qemu_cleanup(int status);
```

### 4.2 启动流程

1. `NativeActivity` 起来 → `APP_CMD_INIT_WINDOW`
2. `vm_engine_on_window_ready()` 从 Intent 里的 `VmConfig` JSON 取出 `imageDir` / `dataDir`
3. 派生出 `kernel` / `ramdisk.img` / `system.img` / `vendor.img` / `userdata.qcow2` 路径
4. 起一个后台线程调用 `qemu_init()` + `qemu_main_loop()`（QEMU 自带事件循环，会阻塞该线程）
5. QEMU 当前以 `-display none` 运行，访客内核日志写到 `<dataDir>/logs/console.log`

### 4.3 链接方式

`CMakeLists.txt` 里用 `--start-group/--end-group` 包住所有静态库（彼此循环依赖）：

```cmake
-Wl,--start-group
  prebuilt/qemu/${ANDROID_ABI}/libqemu_objs.a
  prebuilt/qemu/${ANDROID_ABI}/libqemuutil.a
  prebuilt/qemu/${ANDROID_ABI}/libfdt.a
  prebuilt/qemu/${ANDROID_ABI}/libvduse.a
  prebuilt/qemu/${ANDROID_ABI}/libz.a
  ../jniLibs/${ANDROID_ABI}/libglib-2.0.so   （以及 gio/gobject/gmodule/pixman）
-Wl,--end-group
```

若 `prebuilt/qemu/<abi>/libqemu_objs.a` 不存在，CMake 自动退化为纯骨架，工程仍可编译。

### 4.4 机器类型提醒

上游 QEMU **没有 `ranchu` 机器类型**（Android 模拟器的 QEMU 是打过补丁的下游版）。
我们改用通用 `virt` 平台 + virtio 设备：

```
-M virt -cpu cortex-a57 -m 2048 -smp 4 \
-kernel kernel -initrd ramdisk.img \
-append "console=ttyAMA0 androidboot.hardware=ranchu androidboot.selinux=permissive ..." \
-drive file=system.img,if=virtio,format=raw,readonly=on
```

Android 11 的 AVB / dm-verity 会拦 `system.img`，先用 `permissive` + `veritymode=disabled`
把链路跑通，之后再收紧。

### 4.5 显示后端（vmhost）：已实现

QEMU 侧新增了一个自定义显示后端 `ui/vmhost.c`（由 `build_qemu.sh` 幂等注入），
把访客帧缓冲留在**同进程内存**里，引擎直接取用——不经过 VNC/共享内存/子进程。

注入内容（都写进 `build_qemu.sh`，可重复复现）：

| 步骤 | 动作 |
|---|---|
| a | 拷贝 `scripts/qemu_patches/ui_vmhost.c` → `<qemu>/ui/vmhost.c` |
| b | 拷贝共享头 `src/main/cpp/src/vmhost_display.h` → `<qemu>/include/ui/` |
| c | `ui/meson.build` 的 `files()` 里加 `'vmhost.c'` |
| d | `ui/console.c` 的 `graphic_console_init()` 末尾插入 `vmhost_display_attach(s)` |

**为什么挂在 `graphic_console_init()`**：`ui/console.c` 里所有 `dpy_*` 通知都会先做
`if (con != dcl->con) continue`，所以 `DisplayChangeListener` 必须绑定到具体 `QemuConsole`。
`graphic_console_init()` 正是控制台创建完成、能拿到 `QemuConsole*` 的地方，
在该函数体内用 `extern` 局部声明原型即可完成挂载，无需改动文件头的 include。

引擎侧分工：

```
QEMU 线程（写）                     渲染线程 android_main（读）
dpy_gfx_update/witch ──► 互斥锁 ──► vm_guest_display_poll()
  BGRA→RGBA 转换、拷贝脏区            取帧 → glTexImage2D/glTexSubImage2D
  vmhost_display_copy_frame()         vm_render.c 画带 letterbox 的纹理四边形
```

- 像素格式统一转成 **RGBA8888**（QEMU 的 32bpp 表面在小端内存里是 B,G,R,X，需要交换 R/B 并补 alpha；16bpp 的 r5g6b5 也做了展开）
- 放在渲染线程做 GL：`vmhost_display_copy_frame()` 只是 `memcpy`，不碰 GL，避免跨线程使用 EGL 上下文
- 等比缩放 + 黑边，不会把访客画面拉变形
- 还没拿到帧时，画面是渐变底色（表示引擎活着）

### 4.6 输入回传：已实现

复用同一个 vmhost 后端文件，QEMU 侧多了一个输入段（`ui/vmhost.c` 的输入注入部分），
接口在共享头 `vmhost_input.h`。

**关键点：为什么没有 UI 前端也能注入**
`ui/input.c` 的 `qemu_input_event_send_impl()` 会做
`qemu_input_find_handler(1 << evt->type, src)`，而 `hw/input/virtio-input-hid.c` 在
设备 realize 时会自己调用 `qemu_input_handler_bind()`。所以只要在命令行加上输入设备，
即使用 `-display none`，注入也能正确路由。

**设备**

```
-device virtio-multitouch-pci    ← 触摸屏（绝对坐标 + 多指）
-device virtio-keyboard-pci      ← 按键
```

**数据流**

```
AInputEvent（NativeActivity）
  → vm_input.c 取坐标/键码
  → vm_render_map_to_guest()   抵消 letterbox 等比缩放，得到访客像素坐标
  → vmhost_input_touch / vmhost_input_key
  → qemu_input_queue_mtt / qemu_input_event_send_key_qcode
  → virtio-multitouch / virtio-keyboard
```

**坐标换算必须做**：画面上屏时做了等比缩放 + letterbox，触摸回传要做同样的逆变换，
否则点屏幕的位置和访客收到的位置对不上。所以 `vm_render.c` 会把当帧的
`s_scale_x/s_scale_y` 存下来，供 `vm_render_map_to_guest()` 反算。

**触摸用 MT-B 语义**：每个 slot 一个 `tracking_id`，按下发
`begin(slot, tid)` + `data(x)` + `data(y)`，移动只发 `data`，抬起发 `end(slot, tid)`，
最后统一 `qemu_input_event_sync()`。

**按键**：Android keycode 先查表转成 Linux 键码，再走 QEMU 自带的
`qemu_input_linux_to_qcode()`。目前覆盖 HOME/BACK/方向/ENTER/ESC/音量/菜单等常用键，
未列出的键会被忽略。

**多指**：Android 的 pointer id 取值 0..31 且随手指来去而变化，而 QEMU 的 mtt slot
只有 `VMHOST_TOUCH_SLOTS`(10) 个且要求稳定，所以 `vm_input.c` 维护了一张
**pointer id → slot 映射表**（`s_slot_of_pointer` + `s_slot_used` 位图），
手指按下时分配槽位、抬起时释放：

| 宿主动作 | 处理 |
|---|---|
| `ACTION_DOWN` / `ACTION_POINTER_DOWN` | 从 action 高位取指针索引 → 分配槽位 → 发 `down` |
| `ACTION_MOVE` | 遍历**全部**指针，各自更新位置（一次事件可能带所有手指） |
| `ACTION_UP` / `ACTION_POINTER_UP` | 取指针索引 → 发 `up` → 释放槽位 |
| `ACTION_CANCEL` | 释放全部触点 |

另外窗口销毁（`APP_CMD_TERM_WINDOW`）时也会 `vm_input_release_all()`，
避免访客侧留下「按下去就不放」的残留触点。

### 4.7 网络：已实现（QEMU 用户态 NAT）

用 QEMU 内置的 **slirp 用户态 NAT**，而不是宿主侧 VpnService：

```
-device virtio-net-pci,netdev=net0
-netdev user,id=net0
```

访客通过 DHCP 拿到 `10.0.2.15`，网关 `10.0.2.2`，DNS `10.0.2.3`；
slirp 在 QEMU 进程内把访客的 TCP/UDP 直接转成宿主 socket，
**不需要任何 Android 网络权限，也不需要 VpnService**。
`VmConfig.netMode` 为 `NONE` 时不挂这块网卡。

`libslirp.so`（143 KB）由 `build_qemu.sh` 的依赖收集自动带进 `jniLibs`，
`libvmengine.so` 的 `DT_NEEDED` 里能看到它。

> **为什么不用 VpnService**：VpnService 给的 tun fd 是**应用侧**的 tun，
> 交给 QEMU 用不了；要让它工作，得在引擎里自己实现一套用户态 NAT
> （ARP 应答 + 源地址改写 + 校验和重算），工作量和出错面都大得多。
> `VmNetworkService` 先保留，留给以后需要「访客流量走宿主网络栈」的场景。

### 4.8 停机：已实现

**为什么必须做**：QEMU 跑在独立线程里，`android_main` 返回并不会带走它。
如果只是让 Activity finish，进程会被 QEMU 线程一直吊着 —— 实例根本停不下来，
而且 `userdata` 镜像也不会被刷写。

**做法**：让 QEMU 走它自己的正常退出路径。

QEMU 侧（`ui/vmhost.c`，接口头 `vmhost_control.h`）：

```c
void vmhost_control_request_shutdown(void)
{
    qemu_system_shutdown_request(SHUTDOWN_CAUSE_HOST_SIGNAL);
}
```

查过 `system/runstate.c` 的 `main_loop_should_exit()`：拿到 `shutdown_requested` 后，
只有 `shutdown_action == SHUTDOWN_ACTION_PAUSE`（即启动时带了 `-no-shutdown`）
才会转成暂停；**我们没传 `-no-shutdown`，所以主循环直接返回**，
随后引擎调用 `qemu_cleanup()` 收尾刷盘。这条路径**不会给访客发 ACPI 关机、
也不等访客响应**，所以 Android guest 不配合也不会卡住。

引擎侧（`vm_qemu.c`）的 `vm_qemu_stop(timeout_ms)`：先请求停机，再轮询等待主循环返回
（用轮询而不是 `pthread_timedjoin_np`，避免依赖 bionic 非标准扩展），
最后 `pthread_join` 回收线程；join 用 `s_joined` 保护，保证只做一次。

**两个触发点**：

- `APP_CMD_DESTROY`（Activity 正在销毁）—— 这是主路径，Java 侧「停止」按钮
  走 `finishAndRemoveTask()` 就会到这里
- `android_main` 主循环退出后的兜底调用 —— 覆盖 Activity 被系统直接回收的情况

等待上限 5 秒；超时只告警不阻塞，进程最终由系统回收。

### 4.9 还没做的

- **性能**：每帧 `memcpy` + 全量纹理上传，后续可改成按脏区上传（`glTexSubImage2D` 带偏移）。
- **后台暂停**：目前只有停机，没有在 App 切到后台时暂停 QEMU 省电。

## 7. 访客启动链路：把 `sys.boot_completed` 跑出来（TCG，无 KVM）

> 本章与第 4 章的显示/网络**实现**无关，讲的是「怎么让访客真正启动完成并稳住」。
> 注意：本章实验走的是 **AOSP 自编译 QEMU**（`emu-34`/`ranchu`，arm64 二进制，`-M ranchu`），
> 与 4.4「上游 QEMU 用 `virt`」是两条并行路线。

### 7.0 场景与总难点

主机是 Android 手机（arm64，**无 `/dev/kvm`**），只能跑 QEMU **TCG 全虚拟化**，访客整体比真机慢 **50–100×**。
由此引出的总矛盾：

```
TCG 慢 → system_server 主线程偶发 >60s 阻塞
services.jar 里 Watchdog.DEFAULT_TIMEOUT 硬编码 60s（无外部属性开关，ro.hw_timeout_multiplier 对它无效）
        → 判定 OVERDUE → Process.killProcess(myPid()) + System.exit(10)
        → zygote 见 system_server 死 → 自杀重启 → 无限循环
        → sys.boot_completed 永不置位
```

三处根因与修复：

| # | 现象 | 根因 | 修复 | 产物 |
|---|---|---|---|---|
| ① | system_server 反复 SIGABRT | 访客里没有 `/dev/input` 目录，EventHub 构造时 `LOG_ALWAYS_FATAL_IF` | 补建该目录 | `vmhost_input.rc` |
| ② | 进程被 SIGKILL、`boot_completed` 反复丢 | Watchdog 硬编码 60s | 在访客内注册 `IActivityController`，让它**只回调不杀** | `vmhost_amctl.jar` / `vmhost_amctl.sh` / `vmhost_amctl.rc` |
| ③ | 每秒级 `flags_health_check UPDATABLE_CRASHING` 风暴 | 无网卡 → `eth0` 不存在 → `dhcpclient_def` 无限重启 | 启动前判断 `eth0` 是否存在 | `ranchu_net.sh` / `inject_vendor_net.sh` |

### 7.1 修复①：访客缺 `/dev/input`（Android 11 起是致命的）

- 症状：system_server 每 ~90–220s 死一次，`zygote` 随之自杀重启；崩溃记录（`/metadata/crash.log`，不是串口）里
  12/12 一致：
  `[ANDROID_LOG_ASSERT] tag=EventHub cond=mInputWd < 0 / Could not register INotify for /dev/input: No such file or directory`。
- 原因：Android 11 起 `EventHub` 构造函数对「`/dev/input` 目录不存在」是**致命**的；本访客无任何输入设备
  （`-display none`、无 virtio-input），`ueventd` 从不创建该目录。
- 修复：`vmhost_input.rc` 注入 `/system/etc/init/`，在 `early-init` / `post-fs` / `boot` 三处
  `mkdir /dev/input 0775 root input`（EventHub 只是 inotify 监听该目录，空目录即可）。

### 7.2 修复②：Watchdog 只回调不杀（注册 `IActivityController`）

`Watchdog.run()` 里**唯一**能让它不 `killProcess` 的正规口子是 `mController`：

```java
IActivityController controller;  // = mController
if (controller != null) {
    int res = controller.systemNotResponding(subject);
    if (res >= 0) { waitedHalf = false; continue; }   // >=0 → 继续等待，永不杀
}
```

反例（都验证过不可用）：`am monitor` 内置控制器的 `systemNotResponding` 明确 `return -1`（放行击杀）；
`setAllowRestart(false)` 唯一入口是 `AMS.hang()`，而 `hang()` 全程 `synchronized(AMS)`＝持全局锁，会把整机锁死。

**实现**：`amctl/vmhost/AmController.java`，以 `app_process` 运行（自带 binder 线程池，`main` 可 sleep，
回调在 binder 线程到达）。隐藏 API 全走反射，控制器对象用 `java.lang.reflect.Proxy` 实现隐藏接口
`android.app.IActivityController`（避免把 `android.app.*` 重复类打进 dex），`asBinder()` 返回自写的 `Binder`。

| 交付物（注入 `/system/...`） | 说明 |
|---|---|
| `framework/vmhost_amctl.jar` | dex，类 `vmhost.AmController` |
| `bin/vmhost_amctl.sh` | `export CLASSPATH=...; exec app_process /system/bin --nice-name=vmhost_amctl vmhost.AmController` |
| `etc/init/vmhost_amctl.rc` | `service vmhost_amctl /system/bin/sh /system/bin/vmhost_amctl.sh`，`user root`，`seclabel u:r:incidentd:s0`，`on zygote-start start` |
| `build_amctl.ps1` | 构建：JDK17 `javac -encoding UTF-8` → `d8` → `jar`（**必须显式 UTF-8**，否则 Windows 默认 GBK 报"不可映射字符"） |

`IActivityController` 的 6 个事务码（用 `aidl.exe` 编译 r48 的 `.aidl` 得到，**不要靠猜**）：

| 事务 | 码 | 本实现返回值 |
|---|---|---|
| `activityStarting` / `activityResuming` / `appCrashed` | 1 / 2 / 3 | `true`（正常放行） |
| `appEarlyNotResponding` | 4 | `0`（继续，不杀） |
| `appNotResponding` | 5 | `1`（继续等待，不弹窗） |
| **`systemNotResponding`** | **6** | **`0`（继续等待，永不 SIGKILL）** |

程序每 2s 重注册一次（system_server 重启会丢弃控制器，靠重注册自愈）。

**两个必须踩过才知道的坑**：

1. **init 会拒绝启动"无标签的脚本"服务**：报
   `File /system/bin/vmhost_amctl.sh(labeled "u:object_r:unlabeled:s0") has incorrect label or no domain
   transition from u:r:init:s0 ...`。解决：service 里显式写 `seclabel`（见 7.4 另一处同类问题的无损解法）。
2. **域选错 → `ServiceManager.getService("activity")` 恒为 `null`（且无异常、无 avc，极难查）**。
   `hal_graphics_composer_default` 在 sepolicy 里**没有任何 `service_manager find` 权限**，拿不到服务。
   改用 **`incidentd`** 后立即成功，依据（从 `/system/etc/selinux/plat_sepolicy.cil` 查得）：
   `(allow incidentd system_server_service (service_manager (find)))`（`activity_service` ∈ 该 attr）、
   `(allow incidentd system_server (binder (call transfer)))`（我们向 AMS 注册）、
   `(allow system_server incidentd (binder (call transfer)))`（**AMS/Watchdog 反向回调 `systemNotResponding` 必需**）。
   `statsd` / `notify_traceur` 也满足，可作备选。
   排查手法：`audit=0` 会把 SELinux 拒绝藏起来，查这类问题时**先从 cmdline 去掉**；并在程序里打印
   `ServiceManager.listServices()`（能列出则 servicemanager 可达）+ 逐个 `getService(name)`（判断 find 是否被拒）。

另外本实验的 rdinit 是自定义的（`rdinit=/dumper`，见 7.5），init 未必采纳 cmdline 里的
`androidboot.selinux=permissive`；故在 `vmhost_amctl.rc` 里用 init 的 `write /sys/fs/selinux/enforce 0` 显式兜底
（init 对 selinuxfs 有 file write 权限）。

**验证判据**：`controller registered` 出现后，看门狗每次触发都应只回调、不杀——

```
controller registered (attempt#86)                                        @405.6s
vmhost_amctl: systemNotResponding -> keep waiting: Blocked in handler on main thread (main)  @598.1s
grep -c 'WATCHDOG KILLING'  →  0        grep -c 'Entered the Android system server'  →  1（SS 从未重启）
```

长时间实测：单 system_server / 单 zygote 连续跑到 guest **6562s（≈109 分钟）**，0 次看门狗击杀、0 次 ANR。

### 7.3 修复③：`dhcpclient_def` 无限重启 → `flags_health_check` 风暴

现象（9.1 小时窗口）：`dhcpclient_def` 被启动 **5787** 次，`flags_health_check UPDATABLE_CRASHING`
被阻塞式 `SVC_EXEC` 了 **5258** 次（占日志 26282 行）——全访客只有这一个重启循环。因果链：

1. 实验的 QEMU 命令行**没给网卡**（只有 virtio-blk ×6 + virtio-rng + virtio-gpu）→ 访客内**不存在 `eth0`**。
2. vendor 的 `/vendor/bin/init.ranchu-net.sh`（由 `on property:qemu.networknamespace=ready` 启动）在
   `ro.kernel.qemu.wifi != 1` 时执行 `setprop ctl.start dhcpclient_def`。
3. `service dhcpclient_def /vendor/bin/dhcpclient -i eth0 --no-gateway` 打不开 `eth0` → **exit 1**；
   非 oneshot → **init 每 ~7s 自动重启一次**。
4. `dhcpclient_def` 属 "updatable 服务"（`ro.apex.updatable=true`）→ `system/core/init/service.cpp` 的
   `Service::Reap()`：崩溃累计 >4 次就 `SetProperty("sys.init.updatable_crashing","1")`
   （boot_completed 前**任何**第 5 次即触发；之后要求 4 分钟内 5 次——每 7s 崩一次，永远满足）。
5. `apexd` 监听该属性（二进制里含 `sys.init.updatable_crashing`），每次 `Attempting a revert` 并把它**复位**，
   于是下一次崩溃能再次触发（init 的 `on property:` 是边沿触发）——这就是"为何不是只触发一次"。
6. `/system/etc/init/flags_health_check.rc` 的 `on property:sys.init.updatable_crashing=1` →
   阻塞式 `exec /system/bin/flags_health_check UPDATABLE_CRASHING`（init 会 `waiting`），如此循环。

**修复**：把 `/vendor/bin/init.ranchu-net.sh` 的默认分支加 eth0 存在性判断（`ranchu_net.sh`）：

```sh
    *) if [ -e /sys/class/net/eth0 ]; then
           setprop ctl.start dhcpclient_def
       fi
       ;;
```

管线 `inject_vendor_net.sh`：`vendor_bt2.img` → `vendor_bt3.img`。**注意**：若给访客接了网卡（4.7 的 NAT 路线），
`eth0` 存在，本判断自动放行，行为与上游一致。

**验证**：`start ranchu-net` 正常 succeeded、`ranchu-net` exit 0；`dhcpclient` 计数 **0**、`UPDATABLE_CRASHING` 计数 **0**；
**附带收益**：去掉这几千次阻塞 init 的 `SVC_EXEC` 后，`sys.boot_completed=1` 从 ~1180–1400s **提前到 <655s**。

### 7.4 通用经验：改镜像里「被 init 当 service 启动」的文件，必须还原 SELinux 标签

用 `debugfs` 的 `rm` + `write` 替换文件会**新建 inode**，从而**丢掉 `security.selinux`**。此时 init 的用户态检查
（与内核 enforcing 无关，permissive 下同样会拦）会拒绝启动：

```
File /vendor/bin/init.ranchu-net.sh(labeled "u:object_r:unlabeled:s0") has incorrect label
or no domain transition from u:r:init:s0 ...  →  Could not start service
```

两种解法：

| 解法 | 做法 | 适用 |
|---|---|---|
| 加 `seclabel` | 在 service 定义里显式指定域，如 `seclabel u:r:incidentd:s0` | 新建自己的 service（见 7.2） |
| **还原标签（推荐）** | 从**原 inode** 读标签写到**新 inode** | 替换上游已有文件，行为零变化 |

还原标签用 `debugfs` 1.47 的 `ea_get/ea_set`（不写死标签值）：

```bash
# 在源镜像上读出标签；在目标镜像上写回（值含结尾 NUL）
debugfs -R "ea_get -f /tmp/lbl.bin <file> security.selinux" src.img
debugfs -w -R "ea_set -f /tmp/lbl.bin <file> security.selinux" dst.img
# 参考值：/vendor/bin/init.ranchu-net.sh = u:object_r:goldfish_setup_exec:s0
```

### 7.5 复现与验收

实验启动脚本 `exp47.sh`（放在设备 `/data/local/tmp/`，日志 `g47.log`，进度 `exp47.txt`）。要点：

```sh
IMG=/data/user/0/com.vm.app/files/images/p11_arm64     # kernel/ramdisk 来自这里
/dev/vexp/qemu-system-aarch64 \
  -M ranchu -cpu cortex-a57 -smp 6 -m 4096 \
  -kernel "$IMG/kernel" -initrd /data/local/tmp/ramdisk_probe.img \
  -append "console=ttyAMA0 androidboot.hardware=ranchu androidboot.selinux=permissive \
           androidboot.veritymode=disabled androidboot.force_normal_boot=1 rdinit=/dumper \
           ignore_loglevel panic=0 printk.devkmsg=on audit=0" \
  -drive ...（data / metadata / system_ext / product / vendor / system，均 cache=unsafe，只读盘 readonly=on）\
  -device virtio-blk-device,drive=...（×6） -device virtio-rng-device -device virtio-gpu-device \
  -no-reboot -display none -monitor none -serial file:g47.log
```

验收判据（都在串口日志里 grep）：

| 判据 | 期望 |
|---|---|
| `sys.boot_completed=1` | 出现（属性动作若干处） |
| `OnBootPhase_1000` | 出现 |
| `Entered the Android system server` | **1**（SS 从未重启） |
| `*** WATCHDOG KILLING` | **0** |
| `Sending signal 9 to service 'zygote'` | 0（zygote 从未重启） |
| `dhcpclient` / `UPDATABLE_CRASHING` 行数 | 0 / 0 |
| `vmhost_amctl:` 日志 | 仅 5 行（`start` → `waiting for 'activity'` → `controller registered` → 每次 `systemNotResponding -> keep waiting`） |

镜像重建管线（脚本都在 `vm/build-aosp-exp/`，在 WSL 里跑）：

```bash
bash build_crashlite.sh && bash inject_system_crash.sh   # 产物 system_bt.img（含 /dev/input rc、crashlite、amctl）
bash inject_vendor_net.sh                               # 产物 vendor_bt3.img（ranchu-net 补丁）
```

三个产物分别推给设备：`system_bt.img` → `/data/local/tmp/system.img`，`vendor_bt3.img` → `/data/local/tmp/vendor.img`（`exp47.sh` 从这两个路径起 QEMU）。

**含 `audit=0` 的取舍**：`audit=0` 会隐藏 avc 拒绝（排查 SELinux 时要临时去掉）；但全程 permissive 时
它是一个纯降噪项（关掉它那轮日志 0.81KB/s、开 0.57KB/s），**且能避免拒绝日志挤占 logd 环缓冲**——
上一轮关掉 audit 时 `StartSystemUI`、`OnBootPhase_600` 起始行就是这么被挤掉的。

### 7.6 App 侧：子进程跑 AOSP QEMU（B1）—— 手机 App 里也能到 `sys.boot_completed=1`

**为什么 7.5 的修法不能直接搬进 App**：App 引擎链的是**上游 QEMU（`-M virt`）**，而这套访客是
ranchu/goldfish 配的 —— 它的 `vendor.hwcomposer-2-3`（EmuHWC2）依赖 goldfish pipe/gfxstream，
在 `virt` 下反复 abort → `onrestart` 重启 surfaceflinger → surfaceflinger 的 `onrestart` 又重启 zygote →
系统永远到不了 boot。实测 App 内 `virt` 只能到 zygote 阶段就被这串连锁打崩。

**B1 的做法**：不用进程内嵌的上游 QEMU，改为 `fork/exec` **已验证的 AOSP QEMU（ranchu）独立二进制**
（`prebuilt/qemu-aosp/arm64-v8a/qemu-system-aarch64`，112MB；AOSP QEMU 只有二进制、无可链静态库）。
引擎改动都在 `engine/src/main/cpp/src/vm_qemu.c`（spawn 模式）：

- 二进制随包分发为 `libqemu_exec.so`，落在 `nativeLibraryDir`（Android 上**唯一允许 app 执行**的位置；
  宿主 SELinux Enforcing，`/data/local/tmp` 是 `shell_data_file`，app 域不能 exec）。
- 引擎用 `dladdr` 取自身 .so 所在目录（= nativeLibraryDir），`file_ok()` 命中 `libqemu_exec.so` 就走
  子进程模式；没命中才退回进程内嵌（`-M virt`）老路径。
- 子进程 `setenv("LD_LIBRARY_PATH", nativeLibraryDir)`（AOSP QEMU 依赖同目录的 glib/pixman 等）。
- `vm_qemu_stop()` 对子进程先 SIGTERM、超时再 SIGKILL（AOSP QEMU 没有 vmhost 停机通道）。

**踩过的坑（都有实测证据，照做即可）**：

| 坑 | 现象 | 处理 |
|---|---|---|
| Android `JSONObject.toString()` 把 `/` 写成 `\/` | 引擎 `json_get_string()` 不反转义 → 路径带反斜杠 → `access()` 失败 → "内核不存在或不可读" | `json_get_string()` 加 JSON 反转义 |
| 缺 `<dataDir>/logs/` | QEMU `-serial file:` 的 chardev 建文件失败 → QEMU 直接退出、实例进程消失 | 启动前 `mkdir`（引擎里做） |
| App 默认只挂 system/vendor/userdata 三块盘 | first-stage 报 `partition(s) not found ... metadata` → `InitFatalReboot` | 补 `product`/`system_ext`/`metadata`，共 6 块（`vm_qemu.h` + `vm_engine.c` 增加路径） |
| `-M virt` 盘序 = 命令行顺序；**`-M ranchu` 盘序 = 反序** | 实测 exp47：先挂 data 得到 vdf、最后挂 system 得到 vda | B1 挂盘顺序必须是 `data, metadata, system_ext, product, vendor, system`（恰好满足访客 fstab：vda=system…vdf=data） |
| cmdline 照 exp47 抄 | 多了 `root=/dev/vda` 会触发 `Unable to move mount at '/dev'` → InitFatalReboot | `rdinit=/dumper` + **不带 `root=`** + `audit=0` |
| `-netdev user,id=net0` | 这台 AOSP QEMU 报 `Parameter 'type' expects a netdev backend type` 并退出 | B1 先**不带网络**（ranchu-net 补丁保证无 eth0 也正常） |

**自包含 APK**：把 `libqemu_exec.so`（strip 后 18MB）+ `libgthread-2.0.so` + `libpcre2-posix.so` +
`libc++_shared.so` 放进 `engine/src/main/jniLibs/arm64-v8a/`，`useLegacyPackaging=true` 解压进
nativeLibraryDir → **装完即用，无需 root 手动拷**（注意：每次 `adb install -r` 会重建该目录）。
glib/pixman 等用 jniLibs 里同一套（AOSP 版）即可，引擎（上游 QEMU 对象）与它链接兼容。APK 约 30.5MB。

**验收判据**（与 7.5 同一套，全部在 App 实例的 `files/vms/vm_1/logs/console.log` 里 grep）：

| 判据 | 期望 |
|---|---|
| `sys.boot_completed=1` | 出现（属性动作若干处） |
| `Entered the Android system server` | **1**（SS 从未重启） |
| `*** WATCHDOG KILLING` | **0** |
| `vmhost_amctl: controller registered` | 出现 |
| `vmhost_amctl: systemNotResponding -> keep waiting` | 出现（Watchdog 只回调不杀） |

**当前取舍**（B1 的边界）：

- 显示/输入：B1 是 `-display none`，访客画面没回传（vmhost 显示后端只在进程内嵌时有效）→ 显示回传是下一步大项。
- 网络：先不带 NIC。
- `memoryMb/cores`：引擎里硬编码 2048/4，VmConfig 里的数值被忽略（潜在小 bug，待修）。
